# 记忆项目隔离与人工晋升 设计文档

**目标：** 让记忆真正按项目隔离可见和检索，并把短期记忆的长期化改为“7 天命中阈值触发 review、人工确认晋升”的流程，同时从源头减少无记忆点的短期记忆。

**架构：** 保留 `Memory.project_id` 作为项目边界，在服务端和前端统一默认使用当前项目范围；短期记忆只允许承载项目规则/约束/坑点/边界，命中统计直接落在 `Memory` 主表上，7 天窗口达到阈值后转入 `review + short`，人工确认后再升为 `active + long`，拒绝则直接删除。

**技术栈：** FastAPI · SQLAlchemy · MySQL · APScheduler · 现有 OpenAI-compatible 内部 API · Mobile Web

---

## 设计目标

本次设计解决四个现有问题：

1. **项目边界不可靠**：当前搜索虽然支持 `project_id`，但 hook 侧仍依赖 `cwd` 最后一段目录名近似推断，项目隔离不严格。
2. **短期记忆产出过多**：现有提炼输入偏工具流水，容易生成没有“记忆点”的短期记忆。
3. **长期晋升信号过粗**：当前是基于时间自动 short→long，没有使用“被反复命中”的真实使用信号。
4. **审核链条不匹配目标**：`review` 目前更接近复查/降级语义，不适合“值得长期化，等待人工确认”这一新目标。

本次设计的核心原则：

- 记忆是**项目级资产**，默认只能在当前项目内被看到、检索和审核。
- 短期记忆不是会话流水，而是**项目规则 / 约束 / 坑点 / 边界**。
- 长期记忆不能自动生成，必须先进入 `review`，再由人确认。
- 被拒绝的短期记忆直接删除，不保留 `rejected` 审计状态。

## 生命周期设计

### 目标状态

| status | tier | 含义 |
|------|------|------|
| `pending` | `short` | 新提炼出的候选短期记忆，等待人工初筛 |
| `active` | `short` | 已启用的短期记忆，参与当前项目搜索与注入 |
| `review` | `short` | 7 天内命中达到阈值，等待人工确认是否升长期 |
| `active` | `long` | 已人工确认的长期记忆 |

### 删除规则

- 任意短期记忆若被人工拒绝，**直接物理删除**。
- 本设计下不再把 `rejected` 作为常规可见状态参与前端列表和生命周期流转。

### 生命周期流转

```text
提炼写入 -> pending/short
     ↓ 人工启用
  active/short
     ↓ 7 天窗口命中次数达到阈值
  review/short
     ↓ 人工确认
  active/long

pending/short --拒绝--> 删除
review/short --拒绝--> 删除
```

### review 语义调整

`review` 的新语义固定为：

> 这是一条已经被证明反复命中的短期记忆，可能值得长期化，但必须由人工确认。

它不再表示“长期记忆待复查降级”。

## 项目隔离与可见性

### 默认规则

- `/memory/search` 默认只在**当前项目**范围内返回结果。
- `/memory` 列表页默认只展示**当前项目**的记忆。
- 审核动作（启用、升长期、删除）默认只操作当前项目视图中的记忆。

### 管理端例外

移动端/管理端允许切换一个显式范围：

- `当前项目`
- `全部项目`

其中：

- `当前项目` 是默认值。
- `全部项目` 仅用于管理和审查，不改变 hook 注入逻辑。
- hook 搜索始终按当前项目检索，不允许跨项目注入记忆。

### 项目上下文来源

优先级建议如下：

1. 通过 `session_id -> Session.project_id` 获取明确项目
2. 若会话尚未绑定项目，再回退到 `cwd` 推断
3. 若两者都没有，则只在管理端允许全局视图，hook 搜索不走全局降级

这样可以逐步减少当前 `cwd` 近似推断带来的误命中。

## 数据模型变更

### Memory 表新增字段

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `hit_count_7d` | INT | `0` | 当前滚动 7 天窗口内的命中次数 |
| `last_hit_at` | DOUBLE / nullable | `NULL` | 最近一次被搜索结果返回给 Agent 的时间戳 |
| `review_reason` | VARCHAR(64) / nullable | `NULL` | 进入 review 的原因，初始固定为 `hit_threshold` |
| `review_hit_count` | INT / nullable | `NULL` | 进入 review 当时的命中次数快照 |

### 保留字段

- `project_id`：继续作为项目边界的主键字段之一
- `tier`：继续保留 `short/long`
- `status`：保留 `pending/active/review`，不再依赖 `rejected` 做常规流转

### 为什么不单独建命中明细表

本期先不引入 `memory_hits` 明细表，原因如下：

- 当前最急需的是“按项目隔离”和“为什么进入 review”，主表聚合字段已足够支撑
- 改动更小，更容易与现有实现对接
- 后续若需要展示命中来源、按 session 追踪、做细粒度统计，再升级为独立命中日志表即可

## 命中统计规则

### 命中定义

“命中”定义为：

> 一条 `active + short` 记忆被 `/memory/search` 返回，且实际作为结果交给 hook 注入给 Agent。

以下情况**不算命中**：

- 仅搜索词匹配，但未进入返回结果
- 前端手动浏览记忆列表
- `pending`、`review`、`active + long` 状态的记忆被查看

### 7 天窗口算法

采用滚动近似窗口，不做逐日明细聚合：

- 若 `last_hit_at` 为空：
  - 设 `hit_count_7d = 1`
  - `last_hit_at = now`
- 若 `now - last_hit_at > 7天`：
  - 旧窗口失效
  - 重置为 `hit_count_7d = 1`
  - `last_hit_at = now`
- 若仍在 7 天窗口内：
  - `hit_count_7d += 1`
  - `last_hit_at = now`

### review 触发条件

仅对 `active + short` 生效：

- 若 `hit_count_7d >= N`（阈值可配置，先使用固定常量）
- 则：
  - `status = review`
  - `tier` 保持 `short`
  - `review_reason = "hit_threshold"`
  - `review_hit_count = hit_count_7d`

### 人工审核结果

- `review + short -> active + long`：人工确认值得长期保留
- `review + short -> 删除`：人工拒绝

不提供“继续留在 review 中不处理”的额外分支，先保持状态机简单。

## 前端与管理视图

### 默认视图

记忆页默认使用“当前项目”范围，而不是全局范围。

项目范围来源建议：

1. 若用户当前打开某个 session 的聊天页，则使用该 session 的 `project_id`
2. 若未打开聊天页，则使用最近活跃 session 的 `project_id`
3. 若无法确定项目，则回退到空状态提示，而不是默认全局

### 顶部范围切换

记忆页顶部新增范围切换：

- `当前项目`
- `全部项目`

切到“全部项目”时：

- 列表展示所有项目的记忆
- 每条卡片必须显式显示所属项目
- 审核仍允许操作，但用户能清楚知道自己在处理哪个项目的记忆

### 记忆页主分区

推荐拆为 3 个区：

1. **待启用**
   - 数据：`pending + short`
   - 操作：`启用`、`删除`

2. **待晋升审核**
   - 数据：`review + short`
   - 操作：`升为长期`、`删除`
   - 额外展示：
     - 7 天命中次数
     - 最近命中时间
     - 进入 review 的原因

3. **已启用**
   - 数据：`active`
   - 支持二级筛选：`全部 / 短期 / 长期`

### 卡片信息重点

为了突出“记忆点”而不是流水，卡片应重点展示：

- 标题
- 内容
- 所属项目
- 层级标签：短期 / 长期 / 待晋升
- 命中信息：例如“7 天 4 次 · 最近命中 2 小时前”

弱化以下信息：

- 源 session 的技术细节
- 提炼过程
- 纯创建时间排序的存在感

## API 设计调整

### `GET /memory`

保留并强化现有过滤能力：

- `project_id`
- `status`
- `tier`

前端默认总是带当前项目的 `project_id`，只有切到“全部项目”时才不带。

### `GET /memory/search`

保持入口不变，但行为调整为：

1. 仅在当前项目内查询
2. 只返回 `active` 记忆
3. 长期优先、短期补足的策略可以保留
4. 返回结果后，对命中的 `active + short` 记忆更新命中统计，并在达到阈值时自动转入 `review`

### `PATCH /memory/{id}`

语义建议收敛为：

- `pending -> active + short`
- `review + short -> active + long`
- `删除` 不再通过 `status=rejected` 暴露为常规状态流转，而是直接删除接口或 PATCH 内部走删除语义

### 删除接口

建议新增明确的删除行为（REST 语义更清晰）：

- `DELETE /memory/{id}`

用于：

- 拒绝 `pending + short`
- 拒绝 `review + short`
- 人工移除不再需要的短期或长期记忆（如后续要支持）

如果暂时不想新增 DELETE，也可保留 PATCH 触发删除，但前端和设计文档中应明确“拒绝 = 删除”。

## 源头减噪：提炼输入与准入规则

### 现状问题

当前提炼输入主要来自最近 20 条工具事件的摘要拼接，这种输入天然偏向：

- 操作流水
- 临时现象
- 工具噪音

因此即使模型执行正常，也容易生成“没有记忆点”的短期记忆。

### 输入收缩策略

提炼输入应从“工具流水视角”改为“结论视角”，优先保留：

- assistant 的结论性回答
- 用户明确确认的项目规则/约束
- 经过验证的坑点和边界条件
- 少量必要的工具证据（仅用于支撑结论）

应尽量去掉：

- 完整 Bash 输出
- Read/Edit/Write 的细节流水
- 纯文件修改轨迹

### 短期记忆允许生成的内容

短期记忆只允许来自以下三类：

1. **项目约束**
   - 某接口必须带什么字段
   - 某数据库版本不支持什么语法
   - 某流程必须满足什么前置条件

2. **稳定坑点**
   - 某操作会稳定导致什么问题
   - 某状态机会产生什么错误后果
   - 某链路在哪种情况下会重复/失效

3. **边界规则**
   - 某能力仅在什么范围内有效
   - 什么情况下不能走某条路径
   - 某类输入必须被排除

### 明确禁止生成的内容

以下三类一律禁止写入短期记忆：

1. **操作流水**
   - 运行了什么命令
   - 改了哪些文件
   - 哪个测试通过了

2. **一次性现象**
   - 某次偶发日志
   - 某次临时报错
   - 没有普遍性的现场信息

3. **代码常识**
   - 从代码中一眼可见的结构
   - 简单函数职责
   - 显然的配置关系

### 服务端二次过滤

不能只靠模型自觉，写库前必须做服务端过滤。

#### 建议通过条件

记忆至少满足以下条件中的大部分：

- 内容包含明显规则性表达：
  - “必须”
  - “不能”
  - “不要”
  - “需要”
  - “仅在”
  - “会导致”
  - “应当”
- 内容长度在合理范围内（例如 20–200 字）
- 标题和内容能单独表达一个明确约束，而不是动作描述

#### 建议拒绝条件

若满足任一项，则直接丢弃：

- 含明显流水词：
  - “运行了”
  - “修改了”
  - “测试通过”
  - “查看了”
  - “读取了”
- 含明显工具痕迹：
  - `Bash`
  - `Read`
  - `Edit`
  - `pytest`
  - 路径堆叠
- 内容空泛，没有清晰约束对象和约束结论

### 数量限制

为了进一步减少噪音：

- 每个 session 最多生成 **1–3 条** 短期记忆
- 若没有满足准入规则的候选，必须返回空数组 `[]`

## 定时任务调整

现有 housekeeping 中“`active + short + 7 天未更新 -> long`”应被移除，因为它与“人工审核为主”的目标冲突。

保留定时任务的职责应改为：

- 可选地清理异常数据
- 可选地重置过久未命中的短期统计
- 不再负责自动 short→long 晋升

也就是说，长期化的唯一入口应该是：

```text
active/short -> review/short -> active/long
```

## 测试策略

### 服务端测试

新增或调整测试覆盖：

1. **项目隔离**
   - `/memory/search` 在带 `project_id` 时只返回该项目记忆
   - `/memory` 默认项目过滤逻辑正确

2. **命中统计**
   - 第一次命中初始化 `hit_count_7d`
   - 7 天内命中递增
   - 超过 7 天后窗口重置

3. **review 触发**
   - 达阈值前保持 `active + short`
   - 达阈值后转为 `review + short`
   - 记录 `review_reason` 和 `review_hit_count`

4. **人工审核**
   - `pending -> active + short`
   - `review + short -> active + long`
   - 拒绝操作直接删除

5. **源头过滤**
   - 操作流水类候选不会写库
   - 一次性现象不会写库
   - 代码常识不会写库
   - 规则/约束类候选可以保留

### hooks 测试

- `pre_tool` 搜索时优先使用会话项目
- 无项目时的回退逻辑符合设计
- 返回记忆后命中统计被更新

### 前端测试

- 默认只显示当前项目记忆
- 切换“全部项目”后显示跨项目数据
- `review` 分区展示命中统计与审核按钮
- 拒绝操作删除记忆而非标记 rejected

## 迁移与兼容建议

### 数据迁移

- 给 `memories` 表补新增字段：
  - `hit_count_7d`
  - `last_hit_at`
  - `review_reason`
  - `review_hit_count`
- 现有旧数据默认：
  - `hit_count_7d = 0`
  - 其余新增字段为 `NULL`

### 旧逻辑兼容

- 旧的 `review + long` 数据若已存在，需要一次性迁移或在代码中兼容处理
- 若当前系统仍使用 `rejected`，前端应停止把它当常规可见状态，而是逐步迁移到“拒绝即删除”模型

---

## 推荐实施顺序

1. 先收紧数据模型与状态机
2. 再改 `/memory/search` 的项目隔离和命中统计
3. 再改前端记忆页的项目范围与 `review` 分区
4. 最后替换提炼 prompt 与服务端过滤规则

这样可以先把“项目隔离 + 审核链条”跑通，再处理“源头减噪”，降低联调风险。
